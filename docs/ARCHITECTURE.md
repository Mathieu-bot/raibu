# Architecture

Single Spring Boot 3.2.2 application (Java 21), one deployable container, PostgreSQL as the only store. Package root
`src/main/java/shi/raibu/shi`. State is in the database except a few in-memory structures listed in section 6, which is why the app runs
as **one instance** (the free Render plan).

```
Browser (SPA)  --HTTPS REST + session cookie-->  Spring MVC controllers --> services --> Spring Data JPA --> PostgreSQL (Neon)
      \--SockJS /ws (STOMP)--> SignalingController --> services --> SimpMessagingTemplate --> /user/queue/*
```

## 1. Packages

| Package | Role |
|---|---|
| `security` | `SecurityConfig` (filter chain, CORS, 401 handling), `CustomOidcUserService` (creates/updates the user at login), `AppOidcUser` (principal name = app user id), `RoleService`, `SecurityAspect` + `@RequireRole` |
| `endpoint` | `RateLimitingConfigurer` (REST rate limit), `RequestLoggerConfigurer`, `endpoint/rest/controller` (REST), `endpoint/rest/dto` |
| `websocket` | `WebSocketConfig` (STOMP broker, 64 KB limit, rate-limit interceptor), `SignalingController` (`/app/*`), `WebSocketPresenceListener` (disconnect grace), message models |
| `service` | `MatchmakingService`, `FeedbackService`, `FriendshipService`, `DirectMessageService`, `NotificationService`, `ReputationService`, `IcebreakerService`, `RateLimiterService`, `Cached*Service` |
| `model`, `repository` | JPA entities and Spring Data repositories |
| `exception` | `GlobalExceptionHandler` (REST error bodies) |
| `config` | `CacheConfig`, `OpenApiConfig` |

The user principal everywhere (REST `Principal`, STOMP `Principal`) is `AppOidcUser.getName()`, the **application user id** (UUID), never the Google `sub`.

## 2. Authentication and request pipeline

1. Google OIDC login (`/oauth2/authorization/google`). `CustomOidcUserService.loadUser` rejects accounts without a verified e-mail, then finds the
   user by `(provider, providerId)` or creates it (`status IDLE`, `banned false`), refreshes e-mail, name, avatar and `lastActiveAt`, and sets the country
   only when it is still empty (so a country chosen by the user survives later logins).
2. The session (`JSESSIONID`) lives in the servlet container (in memory). A restart or a Render sleep invalidates all sessions: users sign in again.
3. REST: Spring Security chain, CORS from `ALLOWED_ORIGINS`, CSRF, then the rate limit interceptor, then the controller. `@RequireRole`
   methods go through `SecurityAspect`, which asks `RoleService` (admin if the user's e-mail is in `ADMIN_EMAILS`).
4. STOMP: the HTTP session principal is attached to the WebSocket session at the SockJS handshake. Inbound frames pass the
   `RateLimitingChannelInterceptor` (100 SEND frames / 10 s per user), then `SignalingController`.

## 3. Data model

PostgreSQL schema managed by Flyway (`src/main/resources/db/migration`, V1 to V12 at the time of writing). Hibernate runs with `ddl-auto: validate`:
an entity change needs a new migration. Ids are `varchar(36)` UUIDs generated by the application.

```
user (table "user")            chat_session                 chat_message
  id PK                          id PK                        id PK
  provider, provider_id          user1_id FK user             session_id FK chat_session
  email, display_name,           user2_id FK user             sender_id FK user
  avatar_url                     status ACTIVE|ENDED          content, sent_at
  country_code, gender           started_at, ended_at
  preferred_languages (csv)
  interests (csv)              session_feedback               friendship
  preferred_genders (csv)        id PK                          id PK
  prefer_same_country            session_id FK                  user_id_1 FK, user_id_2 FK  (sorted: id_1 < id_2)
  search_mode                    from_user_id, to_user_id       created_at
  status IDLE|SEARCHING|         liked                          UNIQUE(user_id_1, user_id_2)
         IN_CHAT|OFFLINE         UNIQUE(session_id, from_user_id)
  banned                       direct_message                 report
  reputation_score               id PK                          id PK
  positive/negative_feedback     sender_id, recipient_id        reporter_id, reported_user_id FK user
  strike_count                   content, sent_at               session_id FK chat_session (nullable)
  created_at, last_active_at                                    reason, description, status PENDING|REVIEWED|ACTIONED
                               notification                     UNIQUE(reporter, reported, coalesce(session,''))
                                 id PK, user_id FK
                                 type, message, data (json text), created_at, read, read_at
```

Notes: `username` and `session_id` on `user` are legacy columns, unused. Friendships are stored once per pair with the smaller id first.
Preference lists are comma separated text. Reputation score is clamped to [-100, 100]: +1 per like received, -3 per dislike,
-20 per actioned report, at most -50 after a ban.

## 4. User and session state machines

**User status** (`user.status`):

```
            /app/search                     match claimed
   IDLE ------------------> SEARCHING ----------------------> IN_CHAT
    ^  ^                      |  ^                              |
    |  +------ /app/stop -----+  +------- /app/next -------+    |
    |                                (endChat, then search)|    |
    +----------------- endChat (caller always; peer only if still IN_CHAT) --+
```

- `startSearching(userId, mode)`: status `SEARCHING`, stores the normalized `search_mode`.
- `stopSearching`: `IDLE`, clears the mode.
- `findRandomMatch`: both users `SEARCHING` -> both `IN_CHAT` in one transaction, with a new `ACTIVE` session.
- `endChat`: session `ENDED`, caller `IDLE`, peer `IDLE` only if it is still `IN_CHAT` (it may already have started a new search). Users in
  `OFFLINE` are left alone. `OFFLINE` is never set by the current code.
- `/app/next` = `endChat` + `startSearching` with the caller's previous mode + a match attempt.
- Socket gone for more than 10 s (last session closed, no reconnect) = `endChat`.
- Banned users cannot search, signal, chat or DM (checked on every STOMP action).

**Chat session** (`chat_session.status`): `ACTIVE` -> `ENDED` (only transition). Created by the match claim, ended by `endChat`, by a new claim that finds
stale `ACTIVE` sessions of either user, or by the disconnect release. Feedback is accepted only on `ENDED` sessions.

## 5. Matchmaking flow

`SignalingController.searchForMatch` (`/app/search`):

1. Banned? send `ERROR USER_BANNED`, stop.
2. `startSearching(userId, mode)` (own transaction, committed so other searchers see the user).
3. `findRandomMatch(userId)` (`@Transactional`):
   1. Load the caller; empty if missing, banned or not `SEARCHING`.
   2. Candidates: `SEARCHING`, `banned = false`, not self, `reputation >= -49`.
   3. `pickCandidate`: score each candidate (same mode +3, same country +2 when `preferSameCountry`, shared language +1, shared interest +2,
      candidate gender in caller's preferred genders +2, caller gender in candidate's preferred genders +2, `reputation / 10`). Take the
      best score at random among ties; if the best score is not positive pick a random candidate.
   4. `claim(callerId, candidateId)` (the locking step below). If the candidate was taken, drop it from the list and retry, at most 5 attempts.
4. On success the controller sends `MATCH_FOUND` to both users (`data` = the other user's id) and an `ICEBREAKER` question to both
   (chosen from the caller's mode, generic list if the mode has none).
5. No match: nothing is sent, the user stays `SEARCHING` until a later `/app/search` or `/app/next` of someone else claims them.

### Locking strategy

The race to avoid: two searchers pick each other, or two searchers pick the same third user, and one user ends up in two sessions.

`claim` runs inside the `findRandomMatch` transaction:

1. `findAllByIdInOrderById([caller, candidate])` takes pessimistic write locks (`@Lock(PESSIMISTIC_WRITE)`, `ORDER BY id`) on both user rows.
   Locking in id order means two concurrent claims over the same pair serialize instead of deadlocking, and claims over overlapping pairs
   queue up behind each other.
2. After the locks are held, re-read which of the two are still `SEARCHING` and not banned (`findIdsByIdInAndStatusAndBannedFalse`). If the
   caller is no longer claimable the method returns empty; if the candidate is not, that candidate is skipped.
3. Close any `ACTIVE` session of either user (`findActiveByUserIds`, status `ENDED`), insert the new `ACTIVE` session, set both users `IN_CHAT`
   with one `UPDATE ... WHERE id IN (...)`.

`endChat` uses the same ordered locking on the caller and the peer, so ending and claiming never deadlock. The `PEER_DISCONNECTED` message is sent after commit
(`TransactionSynchronization.afterCommit`) so the peer never hears about a rollback.

Feedback: `FeedbackService.submitFeedback` locks the session row (`SELECT ... FOR UPDATE`), requires `ENDED`, inserts the feedback with `INSERT ... ON CONFLICT DO NOTHING`
(duplicate = ignored, returns `false`), applies the reputation change, and re-reads the reverse feedback after its own write. Serialization on the session row means two simultaneous
likes always create the friendship exactly once (`createFriendshipIfAbsent` also tolerates a unique violation).

## 6. In-memory state (why one instance)

| What | Where | Effect of a restart |
|---|---|---|
| HTTP sessions | servlet container | everyone signs in again |
| WebSocket sessions and the grace-period timers | `WebSocketPresenceListener` | sockets drop; timers lost, so `IN_CHAT`/`SEARCHING` users can stay stuck until they search/next again (a later claim closes stale sessions) |
| REST rate-limit counters | `RateLimiterService` | reset |
| WebSocket rate-limit counters | `RateLimitingChannelInterceptor` | reset |
| STOMP simple broker (subscriptions) | Spring | clients must reconnect and subscribe again |
| Spring caches `users`, `friends`, `reputations`, `notifications` | `CacheConfig` (`ConcurrentMapCacheManager`) | see below |

Scaling to several instances would need an external broker (STOMP relay), shared sessions and shared rate limits. Not planned.

Caches: `CacheConfig` enables Spring caching, but the `Cached*Service` read methods (`@Cacheable`) have no caller in the request paths; only the evict methods are used
by `FriendshipService` and `ReputationService`. Effectively nothing is cached today. Do not rely on a cache for correctness, and note that caching of ban state
is deliberately avoided: a ban must apply immediately.

## 7. Notifications and moderation data

`NotificationService.notifyUser` saves a `notification` row and pushes the same payload on `/user/queue/notifications` (a push failure is logged, the row stays). Types: `USER_BANNED`,
`USER_UNBANNED`, `REPORT_ACTIONED`, `MATCH_CONFIRMED`, `NEW_DM`. See `docs/SECURITY.md` for the moderation rules.

## 8. Build and runtime

Gradle build, `bootJar` produces `build/libs/app.jar`. The `Dockerfile` has a build stage (JDK 21) and a runtime stage (JRE 21). Configuration comes only from environment variables
(`application.yml`, `application-prod.yml`), see `docs/DEPLOYMENT.md`. Tests are unit tests (Mockito and MockMvc slices), no database is required.
